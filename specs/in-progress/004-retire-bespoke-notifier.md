## Summary

- The watcher's human-review push stops going through this repo's own notifier (Telegram Bot API / OpenClaw webhook / log) and becomes a publish into the shared notification core that already serves trading and agent escalations.
- A matched task event publishes one `agent-escalation` notification with no target; the deployed routing table keeps owning the channel decision (Discord + Telegram today).
- The vault filesystem trigger and the assignee/status/phase filters are untouched — only the delivery call after a match changes.
- Duplicate suppression stays on the watcher side (the core does not dedup) and collapses from three copies into one: same key, same `dedup_ttl` default of 5m.
- Ordering is the load-bearing part: the shared path must carry a real human-review push from this watcher **before** the bespoke notifier is deleted, and that proof is committed to the repo so it predates the deletion commit in git history.

## Problem

`task-watcher` is the last system in the fleet that implements its own delivery channel. `pkg/notify/` holds a second Telegram implementation, an OpenClaw webhook client and a log-only sender, selected by a `type` string in config; every channel change has to be made here as well as in the shared core. The shared core (lib + controller + Discord/Telegram services) already delivers the same push for trading and agent escalations, so this repo carries a duplicate. The hazard is ordering, not difficulty: today's bespoke path is the live human-review push, so deleting it before the shared path provably carries the same push would kill the operator's phone channel silently — no error, no failed deploy, just a notification that never arrives.

## Goal

Every task event that matches a configured watcher entry leaves this process as a single notification published into the shared core, and the repo contains no channel implementation of its own: no Telegram client, no OpenClaw webhook, no per-type sender selection, no token, no chat id. The push reaches the operator through the same core that already serves trading and agent escalations, and the retirement is provably ordered after a live proof of the new path.

## Non-goals

- **No new notification type.** Reuse `agent-escalation`, which the core already registers and the deployed routing table already resolves. No change to the core library, the controller, or the channel services.
- **No IAM change** — no new permission, role, or role binding. The publish path is not IAM-gated; the initiator name is traceability only.
- **No new credential** — no TeamVault key, no token, no chat id in this repo or in any log line.
- **No change to the trigger, the filters, or the empty-assignee / empty-status / nil-phase guard.** This spec changes what happens after a match, not what counts as a match.
- **No dedup inside the core.** Duplicate suppression stays producer-side (delivery core, controller, and channel services are untouched).
- **No migration of the OpenClaw wake semantics.** The `openclaw-wake` watcher exists to wake an agent, not to reach a human; that path retires under its own work. This spec removes the implementation and does not convert a wake trigger into a human push.
- **No new channels** (Matrix, mail, Slack, Google Chat), no retry queue, no publish buffer, no metrics or health endpoint.
- **Do NOT add a per-watcher dry-run, opt-out, or "keep the old channel" flag** — the topic prefix is the test path (dev routing reaches the test channel, prod reaches the real one); a flag that disables the shared path re-creates the bypass this spec removes. Invariant; a future consumer demanding variation needs a separate spec.

## Desired Behavior

1. **Publish on match.** After all entry filters (assignee, statuses, phases) and after the empty-assignee / empty-status / nil-phase guard, each matching watcher entry publishes exactly one notification into the shared core: type `agent-escalation`, no target, non-empty message. One implementation of the publish call, shared by every entry; no per-entry channel code.
2. **Trigger unchanged.** The vault-cli filesystem watch stays exactly as it is: one watch target per configured vault with its tasks directory, `created` / `modified` events only, task read through the existing storage path. No Kafka consumer is added — the process stays a watcher that happens to publish.
3. **Config becomes filter-only.** A watcher entry keeps `name`, `assignee`, `statuses`, `phases`, `dedup_ttl`; it loses `type`, `url`, `token`, `chat_id`. A config that still carries any of the removed fields fails to load with an error naming that field, so a stale config cannot start and silently deliver nothing. `dedup_ttl` keeps its 5m default and its per-entry independence.
4. **Destination from the environment.** `KAFKA_BROKERS` (comma-separated) and `TOPIC_PREFIX` are read from the environment using the fleet-standard names every other producer uses; startup fails with an error naming the missing variable when either is unset or empty. The effective prefix is logged at startup and on every publish, so a wrong-prefix deployment is visible in the log rather than silent.
5. **Dedup owned by the watcher, in one place.** Duplicate suppression lives in a single component keyed on task name + phase, per watcher entry, using that entry's TTL; the window is consumed when the publish is attempted, whether the attempt succeeds or fails. Restart clears the state (unchanged and accepted: the process is stateless apart from this map).
6. **The bespoke path is deleted, not unwired.** `pkg/notify/` (the local `Notifier` interface, its `Notification` type, and the Telegram / OpenClaw / log implementations), the factory's type switch, the notifier mock, the channel fields in config, and the tests that covered them are removed from the tree. The repo ends with no Telegram or OpenClaw HTTP code, no chat id, no bot token, and no per-type sender selection. `go.mod` gains the notification library at a release that registers `agent-escalation` and the Kafka producer plumbing; `docs/dod.md` (README, docs, CHANGELOG) is satisfied.
7. **Ordering gate.** The publish path lands first, is deployed, and is proven live by the operator; the proof is committed to `docs/live-proof-human-review-push.md`. Only then is the bespoke path deleted, in a later commit — the deletion commit's timestamp is later than the proof commit's. Deleting before the proof is a failure of this spec even if every other check is green.

## Constraints

Frozen:

- **Producer contract:** publish a `NotificationPublishCommand` onto the CQRS Kafka command topic through the shared core's command sender — never through the controller's `/send` HTTP bridge (it sits behind Google SSO and is human-browser-only). The initiator name is a constant string naming this producer.
- **Type and routing:** `agent-escalation`; `Target` is nil on every publish — the deployed routing table owns the channel decision, and a non-nil target would override it.
- **No secret, no role:** no TeamVault key, no token, no chat id; no IAM permission, role, or binding is added, because publishing is not IAM-gated.
- **Assumptions:** the shared core is deployed and consuming (lib, controller, Discord and Telegram services on dev and prod); `agent-escalation` is registered in the library's notification types and resolved by the deployed routing tables; the OpenClaw host can reach the same Kafka brokers the controller consumes from.
- **Repo conventions:** Ginkgo v2 / Gomega specs, counterfeiter fakes for local interfaces, factory functions stay pure composition, `github.com/bborbe/errors` for wrapping, structured logging (no `fmt.Printf`).
- **Scope of edits:** only this repo. The library, the controller, the channel services, and the routing tables are not touched.
- **Definition of Done:** `docs/dod.md` applies to the generated prompts; `CHANGELOG.md` carries an entry under `## Unreleased`.

Not frozen — agent decides at impl time: the spoken wording of the message (content requirements are frozen and asserted), the log level of the **per-publish** line (INFO vs DEBUG), and whether the local publisher seam is an interface with a counterfeiter fake or a func adapter.

**One log level is NOT agent-decides:** the **startup** line carrying the effective topic prefix is pinned at **INFO**. ## Security / Abuse Cases

- **Trust boundary:** vault file contents (task filename, frontmatter `assignee`, `status`, `phase`) become a message in a chat operated by the notification core. Only those fields are read; the message must not start including task body text, so a task body cannot inject arbitrary chat content. Treat all of them as untrusted strings — no credentials, no host paths, no tokens are composed into the message.
- **Credentials:** the change removes credentials from this repo (Telegram bot token, OpenClaw webhook token) rather than adding any. Nothing secret is logged: the publish path has no token to log, and the destination (brokers, prefix) is non-secret configuration. No TeamVault key is added.
- **Reachability of the publish path:** publishing is not IAM-gated, so a mis-configured instance can put text on the operator's channels. The mitigation is configuration (brokers + prefix from the environment, fail-fast when missing) and the observable per-publish log line, not authorization.
- **Wrong-prefix misuse:** a dev-prefix publish reaches the test channel, a prod-prefix publish reaches the operator's real channels. The prefix is operator-supplied per deployment; the spec's proof covers both. No input path lets a publisher choose a channel (`Target` is always nil).
- **Bounded work:** a publish attempt is bounded by the watch context and the producer's timeout; a failing or hanging broker must not hot-loop the watcher, and must not terminate the process (exit on publish failure would take the whole human-review channel down).
- **Validation:** the emitted command is validated before sending (type and non-empty message), so an unroutable type or empty message fails locally and visibly instead of being published.

## Do-Nothing Option

Keep the bespoke notifier: this repo keeps a second Telegram implementation, a second OpenClaw client, and a third delivery type to maintain, and every future channel change is implemented twice. The parent goal's payoff ("no channel is ever implemented per-system again") stays aspirational, and the last duplicate channel implementation stays in the fleet. The cost of doing it is bounded — that is why the ordering gate, not the code change, is the part that needs care.
